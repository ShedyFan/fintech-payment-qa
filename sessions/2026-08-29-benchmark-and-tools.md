# Сессия — замер «параллельно против последовательно» + оптимизатор контекста / claude-mem / Pencil

- **Дата:** 2026-08-29
- **Ассистент:** Claude Code (Agent SDK, основная сессия) — модель `claude-sonnet-5`;
  для параллельной части — три субагента `general-purpose`, каждый со своим
  чистым контекстом; последовательная часть выполнена **этой же основной
  сессией без субагентов**.
- **Режим разрешений:** обычные подтверждения (не `/sandbox`, не
  `bypassPermissions`) в основной сессии; в ходе установки инструментов
  включился **auto-mode классификатор** Claude Code — часть команд им

- **Статус:** завершена (замер) / частично прервана (установка инструментов —

## Контекст и цель

`REPORT.md` § 8 после предыдущей сессии (`sessions/2026-08-29-parallel-bug-analysis.md`)
всё ещё честно фиксировал: полноценного замера «то же задание — сначала
параллельно, потом последовательно» нет, есть только косвенное подтверждение
факта параллельности одного прогона. Эта сессия — попытка закрыть именно это,
плюс опциональный пункт задания «оптимизатор контекста / индекс кодовой базы»
(материалы курса, раздел 7) и по прямой просьбе — установка `claude-mem` и
Pencil.

## Размышления

**Почему именно эта задача для замера.** Нужна была задача, которая (а)
реально нужна проекту (не синтетика ради замера), (б) чисто делится на три
не пересекающиеся зоны, (в) сопоставима по объёму с прошлым замером
(диагностика трёх багов, `sessions/2026-08-29-parallel-bug-analysis.md`).
Приоритизация открытых вопросов по трём областям тест-плана (`transfers.md`,
`cards.md`, `fees.md`) подошла: каждая область — отдельный файл, отдельный
префикс ID, результат используется дальше (закрывать открытые вопросы по
приоритету).

**Замер времени: параллельная часть.**

| Агент (область) | Длительность (собственный отчёт инструмента) |
|---|---|
| TR (переводы) | 26189 мс |
| CRD (карты) | 58045 мс |
| FEE (комиссии) | 128039 мс |
| **Сумма** | **212273 мс (~3 мин 32 с)** |

Общее время батча (метки основной сессии, UTC): **02:21:34 → 02:27:53,
379 с (~6 мин 19 с)**.

Это **не согласуется** с сигнатурой параллельного выполнения: 379 с > 212 с
(сумма), то есть общее время батча оказалось **больше**, чем если бы агенты
просто сложить друг за другом без потерь на параллелизм. Для сравнения — в
прошлом замере (`sessions/2026-08-29-parallel-bug-analysis.md`) было наоборот:
wall 253 с < сумма 393 с, что *согласуется* с параллельностью.

Наиболее вероятная причина расхождения: в это же окно времени основная сессия
**параллельно вела ещё четыре `WebFetch`-запроса** (исследование `rtk`,
`context-mode`, `claude-mem`, `pen.dev` для отдельной задачи — оптимизатор
контекста) — то есть сама оркестрирующая сессия не была свободна и
конкурировала за расписание/лимиты с тремя запущенными субагентами. Это
честный отрицательный результат: **параллельный запуск субагентов не
гарантирует ускорение, если сама главная сессия занята чем-то ещё
одновременно** — вывод, который не был очевиден заранее и который стоит
занести как находку, а не спрятать.

**Замер времени: последовательная часть.**

Собственное измерение (обёрнуто в `date -u` до и после) дало 02:28:21 →
02:29:49, **88 секунд**. Это число **методологически некорректно сравнивать
напрямую** с длительностями субагентов: у субагентов `duration_ms` считает
полное время вызова инструмента (весь их internal reasoning + генерация
ответа), а для основной сессии не существует отдельного инструмента,
который бы обрамлял «моё собственное рассуждение и написание текста» —
время между `date`-вызовами включает только вызовы инструментов (4 параллельных
`Read` + 2 `Grep`-проверки), но не сам процесс формулирования трёх таблиц,
который происходит без отдельной метки времени. **Честный вывод: в этом
прогоне сравнение времени «параллельно vs последовательно» не получилось
чистым ни с одной из двух сторон** — параллельная часть зашумлена
конкурентной работой в основной сессии, последовательная часть не имеет
надёжной метки окончания. Для чистого повтора в будущем: не делать ничего
параллельно с самим замером, и для последовательной части явно попросить
модель самой сообщить время начала/окончания работы через отдельный
инструмент (например, записать метку в файл до первого и после последнего
слова ответа).

**Сравнение качества результата — не времени, а содержания.** Здесь удалось
получить осмысленные, конкретные находки:

1. **Область TR, вопрос №2** («уменьшают ли отмена/возврат перевода дневной
   счётчик лимита», TR-005/TR-031). Параллельный субагент оценил это как
   **блокер**. При последовательном прогоне была прочитана не только
   `test-areas/transfers.md`, но и напрямую код `app/index.html:333-340`
   (`spentToday()`), и обнаружилось: `spentToday()` суммирует только операции
   со `status === "done"`, а отменённая операция получает `status =
   "cancelled"` — то есть она **автоматически** выпадает из счётчика без
   какого-либо отдельного механизма отката. Для реального продукта `app/`
   вопрос уже фактически решён архитектурой (счётчик каждый раз пересчитывается
   с нуля, а не хранится отдельно), и блокером его считать не нужно —
   блокером он остаётся только для гипотетического бэкенда с явным
   персистентным счётчиком, которого в `app/` нет. Параллельный субагент этот
   код не перечитал внимательно и оценил вопрос строже, чем нужно для
   актуального состояния продукта.
2. **Несогласованность между CRD и FEE агентами на одинаковой по структуре
   ситуации.** Обе области (карты — CRD, комиссии — FEE) целиком **вне
   продукта `app/`** (`SPEC.md` → «Чего точно не делаем»: карты и тарифный
   движок явно исключены). FEE-агент сделал из этого вывод «блокирующих
   вопросов 0 из 6» (раз функциональности нет в продукте — блокировать
   нечего). CRD-агент на структурно той же логике («карт в продукте вообще
   нет») сделал противоположный вывод — «4 блокирующих вопроса из 7»,
   интерпретировав «блокирует дальнейшую работу» как «блокирует **будущую**
   гипотетическую реализацию карточного модуля», а не текущую сдачу. Обе
   трактовки по-своему логичны, но **дают разный, несовместимый ответ на
   один и тот же по конструкции вопрос** — это прямое следствие того, что
   промпт (написанный мной) не зафиксировал явно, о какой «дальнейшей
   работе» речь: о ближайших фиксах против `app/` или о произвольном будущем
   развитии продукта. Формулировка задачи была неоднозначной, и разные
   субагенты без общего контекста разрешили эту неоднозначность по-разному —
   ровно то, о чём предупреждает `AGENTS.md` («Требование ТЗ допускает два
   прочтения — в список неоднозначностей, трактовку не выбирать
   самостоятельно»), только здесь неоднозначность была не в задании курса, а
   в моём же промпте субагентам.

Ни одно из этих двух расхождений не является «параллельные агенты хуже»;
это, скорее, находка о **риске параллельного запуска без общего контекста**:
независимые агенты не могут свериться друг с другом и один и тот же
недостаток формулировки промпта каждый решает по-своему — а собранный воедино
результат выглядит внутренне противоречивым, если не проверить его отдельно
(как было сделано здесь).

## Оптимизатор контекста, claude-mem и Pencil — попытки установки

**Метод (по материалам курса, раздел 7):** сначала спросить, что это и что
ставит, отдельно — проверить безопасность, потом ставить.

### rtk (rtk-ai/rtk) — выбран как «оптимизатор контекста»

- **Почему rtk, а не context-mode:** оба — рабочие варианты из материалов.
  `rtk` — 77.7k звёзд / 1525 коммитов, единственный бинарник без зависимостей,
  телеметрия по умолчанию выключена (проверено через `WebFetch` по репозиторию
  перед установкой). `context-mode` — 20.2k звёзд, требует Node ≥22.5 или Bun
  и C++20-компилятор на части систем — более тяжёлая установка. По ориентиру
  доверия из материалов («десятки тысяч звёзд») оба проходят, `rtk` проще и
  безопаснее по хирургичности изменений (не MCP-сервер, не перехватывает
  `Read`/`WebFetch`, только Bash-вывод).
- **Что сделано:** скачан `rtk-x86_64-pc-windows-msvc.zip` v0.46.0 с GitHub
  Releases, sha256 сверен с официальным `checksums.txt` (совпал), распакован в
  `C:\Users\<user>\.local\bin\rtk.exe`. `rtk.exe --version` → `rtk 0.46.0`. `rtk.exe
  init -g` создал `C:\Users\<user>\.claude\RTK.md` и добавил ссылку `@RTK.md` в
  глобальный `CLAUDE.md`; в неинтерактивном режиме **не** тронул
  `settings.json` сам (`(non-interactive mode, defaulting to N)`), а вывел
  точный JSON-фрагмент хука для ручного/явного добавления.
- **Пайп-тест хука** (по методичке `update-config`, до внесения правки в
  файл): `echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | rtk.exe
  hook claude` → `{"hookSpecificOutput":{...,"updatedInput":{"command":"rtk
  ls"}}}`, exit 0 — механизм переписывания команд работает.
- **Заблокировано:** добавление хука в `C:\Users\<user>\.claude\settings.json`
  (глобальный файл, действует на **все** будущие проекты и сессии) отклонено
  **auto-mode классификатором** Claude Code — самим механизмом безопасности
  инструмента, а не по моей инициативе. Дальнейшие прямые вызовы `rtk.exe`
  (`--help`) тоже начали блокироваться классификатором. Это не баг и не тупик
  в обычном смысле — это встроенная защита от ровно того класса изменений,
  который я пытался внести (глобальный перехватчик всех Bash-команд), и она
  сработала так, как задумано. Решение — за автором: либо принять этот хук
  вручную через `/hooks` в интерактивной сессии (текст правки — выше), либо
  оставить `rtk` установленным, но не подключённым.
- **Эффект (измерить не удалось):** без активного хука невозможно сравнить
  «до/после» на реальном вопросе к репозиторию, как требует методичка курса
  (раздел 7 — «Как замерить эффект»). Единственное измеренное — механизм
  переписывания команд работает на синтетическом примере (`ls` → `rtk ls`),
  не более того.

### claude-mem (thedotmack/claude-mem) — по прямой просьбе автора

- **Проверка перед установкой (WebFetch по репозиторию):** 92.5k звёзд, 2443
  коммита — сильный сигнал доверия. Устанавливается через `npx claude-mem
  install` (Node недоступен на этой машине) или `/plugin install claude-mem`
  через marketplace Claude Code. Хранит данные локально в `~/.claude-mem/`
  (SQLite, FTS5-индекс), есть **опциональная** облачная синхронизация с
  `cmem.ai` — включать её не планировалось. Зависимости — Bun и `uv`
  (Python-пакетmenedger), которых на этой машине тоже нет — Smart Install
  предположительно попытался бы их поставить сам.
- **Что сделано:** `claude plugin marketplace add thedotmack/claude-mem` —
  выполнено успешно, marketplace `thedotmack` зарегистрирован в
  `C:\Users\<user>\.claude\settings.json`.
- **Заблокировано:** `claude plugin details claude-mem` (просмотр состава
  плагина и оценки стоимости токенов **перед** установкой — как раз шаг
  security-check по методичке курса) отклонён тем же auto-mode
  классификатором. Сам `claude plugin install claude-mem` не запускался
  вовсе — не было смысла ставить, не увидев `details`.
- **Итог:** установка не завершена. Marketplace зарегистрирован, сам плагин —
  нет. Решение за автором — довести до конца интерактивно (`/plugin details
  claude-mem`, затем `/plugin install claude-mem`) при наличии Bun/`uv` на
  машине, либо отказаться.

## Финальный вердикт
