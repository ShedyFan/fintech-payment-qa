## Постановка (что и почему чиним)

### BUG-02 — дневной лимит по дате UTC, а не по местной

`todayKey()` = `new Date().toISOString().slice(0,10)` — `toISOString()` всегда
UTC. В UTC+3 обнуление дневного счётчика происходит в 03:00 местного времени,
ночные переводы попадают во «вчерашний» бюджет лимита.
**Решение (первая редакция):** ключ суток по местному времени устройства
(`getFullYear`/`getMonth`/`getDate`). Формат `YYYY-MM-DD` не меняется —
совместим с уже сохранёнными `op.day`.
**Продуктовое решение — ПЕРЕСМОТРЕНО** в этой же сессии (по просьбе автора) на
**фиксированный деловой пояс МСК (UTC+3, без DST)** — подробно в разделе
«Пересмотр решения по BUG-02» ниже. Причина: лимит — бизнес-правило, оно должно
обнуляться в одну полночь для всех, а не по часам конкретного устройства.

### BUG-03 — разделитель разрядов молча усекает сумму (`1 000` → 1 ₽)

`parseAmount` = `parseFloat(String(value).replace(",", "."))`. `parseFloat`
разбирает читаемый префикс и молча отбрасывает хвост; `isFinite(amount) &&
amount > 0` видит только итог и не отличает «100» от «100, из которого
отброшено „abc“».
**Решение:** строгая regex-валидация всей строки
(`/^-?\d+([.,]\d{1,2})?$/`), иначе `NaN`. В платёжном виджете молчаливое
усечение опаснее явного отказа (списание необратимо, отказ — нет). Поддержка
пробела как разделителя не снимает двусмысленность (`1.234,56` читается двояко)
— выбран строгий отказ. В `doTransfer` — отдельное сообщение о формате до
проверки «больше нуля»; пустой ввод по-прежнему даёт «Сумма должна быть больше
нуля» (сообщение APP-005 не меняется). Знак минуса в регулярке сохранён, иначе
для `-5` сменилось бы сообщение (регрессия APP-005).

### BUG-04 — валидный JSON с неверной схемой роняет историю

`loadState()` проверяет только `typeof parsed.balance === "number"` и
`Array.isArray(parsed.operations)` — форма элементов не проверяется, `{}`
проходит; `renderHistory()` падает на `op.amount.toFixed` каждую секунду
(`setInterval`). Нарушение `SPEC.md` («сброс к начальному, ошибка в консоль не
выбрасывается»).
**Решение:** функция `isValidOperation(op)` (наличие и типы `id`, `recipient`,
`amount`, `fee`, `status ∈ {done, cancelled}`, `createdAt`, `day`); в
`loadState()` — цикл по `operations`, при первом невалидном элементе
`return defaultState()` (**полная отбраковка**, не построчная фильтрация:
`balance` хранится отдельно и не пересчитывается из `operations`, частичная
фильтрация дала бы ложное чувство целостности и ослабила бы `spentToday()` как
бизнес-инвариант — `SPEC.md` описывает контракт как двоичный сброс). Заодно
`isFinite(parsed.balance)` (`typeof NaN === "number"` проходил старую проверку).
Второй барьер — `if (!isValidOperation(op)) continue;` в самом `renderHistory()`.
**За автором (архитектурное):** включать ли `id` в обязательную схему (баг-репорт
не упоминал, включён по факту использования в `cancelOperation`).

## Размышления

- **Почему три бага в одной сессии, а не в трёх.** Правило проекта требует
  отдельную сессию на *правку продукта*, а не на каждый баг. BUG-01 чинился
  один — там фикс затрагивал две функции (`calcFee`, баланс в `doTransfer` и
  `cancelOperation`) и продуктовое решение (режим округления). Здесь три фикса
  строго локальны и не пересекаются; объединение не размывает след работы, а
  постановка на каждый — явная и отдельная (выше).
- **BUG-01 «Задело» закрывается заодно.** Запись в `bugs/BUG-01` отмечала: пока
  сумма с >2 знаками принимается без нормализации, `round2(balance)` может
  разойтись с сохранённым `amount` в 3-м знаке. Regex BUG-03 (`\d{1,2}` после
  разделителя) физически не пропускает такие суммы — дыра закрыта.
- **Экспоненциальная запись (`1e3`)** — открытый вопрос №8 `SPEC.md` и пункт в
  `test-areas/app.md`. Новая грамматика её тоже отклоняет — вопрос закрывается
  побочно.
- **Playwright.** Тесты `tests/payments.spec.js` были заранее написаны так,
  чтобы позеленеть после фикса: APP-009 — ветка `else` (`operations.length === 0`
  → `#msg` не пуст), APP-014 — `.empty` видно, баланс 50000, нет `pageerror`.
  После фикса обе должны стать зелёными без правки ассертов — только шапка-
  комментарий и `tests/README.md`.

## Пересмотр решения по BUG-02: местное время устройства → фиксированный МСК

По просьбе автора решение по часовому поясу дневного лимита **пересмотрено**.

- **Было (первая редакция фикса):** `todayKey()` строил ключ суток по часам
  устройства пользователя (`getFullYear/getMonth/getDate`).
- **Стало:** фиксированный деловой пояс **МСК (UTC+3, без перехода на летнее
  время)** — `new Date(Date.now() + 180*60000)` + `getUTC*`. Ключ суток
  одинаков для всех пользователей независимо от часового пояса их устройства.
- **Почему.** Дневной лимит — бизнес-правило финтех-продукта (рубли, БИК,
  российский контекст). В реальных банках такой лимит обнуляется в полночь
  *расчётного* пояса, а не в локальную полночь клиента, который может быть в
  любом поясе или подкрутить часы. Клиентские часы недоверенные; фиксированный
  МСК — ближе к тому, как это устроено в проде. У этого учебного стенда сервера
  нет, поэтому «серверный пояс» эмулируется константой `LIMIT_TZ_OFFSET_MIN`
  в самом `app/index.html`.
- **Побочный плюс для тестов:** ключ суток теперь **детерминирован** — не
  зависит от того, в каком поясе стоит CI-машина. `seedAndReload()` в
  `tests/payments.spec.js` считает ту же МСК-дату (`mskTodayKey()`), APP-008
  зелёный на любой машине.
- **DST.** У МСК с 2014 года перехода на летнее время нет, поэтому фиксированный
  +3 корректен круглый год. Если пояс расчёта сменят на такой, где DST есть,
  константу-смещение придётся заменить на полноценную работу с TZ-базой.

Зафиксировано в `app/build-brief.md` («Фиксы 2026-08-29»), `bugs/BUG-02`,
`SPEC.md`, `test-plan.md`.

## Прогон APP-011 вживую (реальные 60+ секунд)

По просьбе автора APP-011 прогнан не только через seed, но и **вживую**:
отдельный файл `tests/payments.slow.spec.js` (не входит в `npm test`, запуск —
`npm run test:slow`), `test.setTimeout(120000)`.

Сценарий: перевод → кнопка «Отменить» есть → **ждём 30 сек реального времени**
→ кнопка ещё есть (таймер идёт, а не «никогда не появлялась») → **ждём ещё
33 сек** (итого 63 сек) → кнопки нет; операция на месте, статус «Исполнен»,
баланс `48990.00 ₽` не откатился.

```
> playwright test tests/payments.slow.spec.js
Running 1 test using 1 worker
  ok 1 APP-011 (live) кнопка «Отменить» исчезает после реальных 60+ секунд (1.1m)
  1 passed (1.1m)
```

Wall-time прогона — 64.6 с. Окно отмены реально закрывается по таймеру
`setInterval(renderHistory, 1000)`, а не только по seed-эквиваленту.
