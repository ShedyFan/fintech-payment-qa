## Контекст и цель

`REPORT.md § 5` уже закрывал плюсовой пункт «изоляция с доказательством»:
7 попыток записи за границу песочницы через Bash → `Read-only file system` /
`Permission denied`, коды возврата, контрольная запись внутри проекта → exit 0.
Не хватало отдельного тест-кейса со слайдов 10–11: встроенная песочница
оборачивает **только Bash и его дочерние процессы** (док Claude Code: *"applies
only to Bash commands and their child processes"*), а MCP-серверы host-процесс
запускает отдельно — под wrap они не попадают.

## Размышления

- **Почему нельзя было прогнать «в лоб» в одной сессии.** Для чистого контраста
  нужно: (а) активная песочница `/sandbox`; (б) MCP-сервер с файловой записью.
  В этой сессии нет ни того, ни другого: `/sandbox` не включён (и агент не
  может его включить — это slash-команда в интерактивном терминале), файловых
  MCP в окружении не подключено (`claude-mem:mcp-search` — поисковый, без
  записи; `Claude_Browser` — браузер, без записи в host-FS).
- **Что решил сделать вместо имитации.** Собрать реальный минимальный MCP-сервер
  и прогнать его как процесс — это честно доказывает половину тезиса
  («MCP-сервер пишет по произвольному пути»). Вторую половину («Bash по тому же
  пути — отказ») уже даёт существующий прогон из `REPORT.md § 5` в
  `/sandbox`-сессии. Плюс — готовая пошаговая процедура, чтобы объединённый
  прогон можно было сделать в одну `/sandbox`-сессию (`tools/sandbox-mcp-probe/README.md`).
  Оговорка о том, что объединённого прогона нет, вынесена в `REPORT.md § 5`
  прямым текстом — не выдаётся за то, чего не было.
- **Почему свой сервер, а не готовый filesystem-MCP.** Готовый тянет зависимости
  и внешний код; для теста границы нужен предельно прозрачный артефакт —
  ~70 строк на встроенных модулях Node, весь код читается за минуту.
- **Формат MCP.** stdio + JSON-RPC 2.0, `protocolVersion` `2024-11-05`,
  минимальный набор методов: `initialize`, `notifications/initialized`,
  `tools/list`, `tools/call`. Достаточно, чтобы Claude Code подхватил сервер и
  показал инструмент `mcp__sandbox-probe__fs_write`.

## Использованные инструменты

| Инструмент | Действие | Зачем |
|---|---|---|
| Write | `tools/sandbox-mcp-probe/{server.js,drive.js,README.md}` | Артефакт тест-кейса |
| `node -c` | Синтаксическая проверка server.js / drive.js | До прогона |
| Bash (`echo > %TEMP%/…`, `echo > /etc/…`, `/root/…`) | Проверить, что сессия НЕ песочная | Честно зафиксировать контекст |
| `node tools/sandbox-mcp-probe/drive.js <путь вне репо>` | Полный MCP-хендшейк + `tools/call fs_write` | Доказать, что MCP-сервер пишет за пределы репозитория |

- **Объединённый прогон «Bash отказ / MCP успех» в одной `/sandbox`-сессии** —
  не сделан (нет активной песочницы в этой сессии; см. «Размышления»). Обе
  половины подтверждены по отдельности: отказ Bash — `REPORT.md § 5` (сессия с
  `/sandbox`), обход MCP — прогон выше. Процедура для объединённого прогона —
  `tools/sandbox-mcp-probe/README.md`, шаги 1–3.

## Финальный вердикт

Тест-кейс «песочница накрывает Bash, но не MCP» **собран и прогнан наполовину
вживую**: MCP-сервер `tools/sandbox-mcp-probe/` реально пишет файл за пределами
репозитория (полный вывод — выше), Bash за границу песочницы реально не пишет
(`REPORT.md § 5`). Объединённого прогона в одной `/sandbox`-сессии нет — это
прямо сказано в `REPORT.md § 5`, а не скрыто; готовая процедура приложена.
Плюсовой пункт «изоляция с доказательством» усилен: теперь есть и вывод отказа
Bash, и рабочий MCP-обходчик с кодом на 70 строк.
