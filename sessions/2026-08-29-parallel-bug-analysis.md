## Контекст и цель

`REPORT.md` § 2 честно фиксирует, что обязательный пункт задания «Агенты:
запустить и попробовать» не был выполнен по факту: изначальная формулировка
README «собран несколькими параллельными агентами» не подтверждалась
git-историей — три области теста были разведены через worktree/ветки одним
автором **последовательно**, а не одновременно работающими субагентами.
Единственный ранее зафиксированный субагент — один `general-purpose` на
проверку полноты (`sessions/2026-08-27-regression.md`, шаг 4).

Эта сессия — целевое закрытие пробела: реальный параллельный запуск трёх
независимых субагентов в одной главной сессии, каждый — на свою, не
пересекающуюся зону, с запретом трогать код продукта (это же требование
уже действует в `AGENTS.md` для тестовой фазы — «увидел дефект — он идёт в
баг-репорт, а не в правку»). Задача осмысленная, не искусственная: три
открытых бага (`BUG-02`, `BUG-03`, `BUG-04`) требовали более глубокой
диагностики и конкретного предложения фикса, чем было в исходных
баг-репортах — то, что раньше стояло в разделе «Предлагаемое направление
фикса» одной строкой.

## Размышления

Главный вопрос перед запуском — каким типом субагента обеспечить «не
трогай `app/`». Рассмотрел два варианта: (1) тип `Explore` — read-only по
списку инструментов (нет `Edit`/`Write`), запрет гарантирован механизмом;
(2) тип `general-purpose` с полным набором инструментов и запретом в тексте
промпта. Выбрал второй, хотя это слабее по духу собственного правила проекта
(«правило в файле — это просьба, механизм — режим разрешений и запреты
инструмента», `AGENTS.md`) — по описанию `Explore` он не предназначен для
задачи такого рода («Do NOT use it for code review… or open-ended analysis»,
а здесь именно диагностика с обоснованием и предложением кода, не поиск
файлов). Решил компенсировать слабый механизм проверкой по факту:
после завершения всех трёх агентов явно сверил `git status` в репозитории —
рабочее дерево чистое, ни один агент не записал ничего мимо своего
текстового ответа. Это тот же паттерн, что уже был в проекте на шаге 4
регрессии («изоляция частичная», зафиксировано честно, а не скрыто) —
здесь фиксирую так же.

Второй вопрос — как измерить, что запуск был действительно параллельным,
а не тремя последовательными вызовами одного и того же инструмента. Один
батч-вызов (три обращения к инструменту запуска агента в одном сообщении)
даёт при this асинхронный запуск; доказательство — соотношение общего
времени прогона и суммы длительностей отдельных агентов:

| Агент | Длительность (собственный отчёт инструмента) |
|---|---|
| BUG-02 | 92176 мс (~1 мин 32 с) |
| BUG-03 | 211262 мс (~3 мин 31 с) |
| BUG-04 | 89800 мс (~1 мин 30 с) |
| **Сумма** | **393238 мс (~6 мин 33 с)** |

Общее время от старта первого до завершения последнего (по меткам
основной сессии, UTC): **01:54:52 → 01:59:05, 253 с (~4 мин 13 с)**.

253 с < 393 с (сумма). Если бы агенты выполнялись последовательно, общее
время было бы близко к сумме (плюс накладные расходы каждого старта);
вместо этого общее время близко к длительности самого долгого агента
(211 с) плюс ~40 с накладных расходов на параллельный старт — это и есть
сигнатура параллельного, а не последовательного выполнения. Строгого
контролируемого замера «то же самое задание — сначала параллельно, потом
последовательно» здесь нет (это отдельный необязательный пункт задания,
`REPORT.md` § 8, по-прежнему не выполнен полноценно) — цифры выше не
подменяют его, а только подтверждают факт параллельности этого конкретного
прогона.

Третье: почему именно эти три задачи, а не что-то синтетическое. Взял
три реально открытых бага, потому что (а) это настоящая, а не показная
работа — результат пригодится для будущей фикс-сессии; (б) зоны
естественно не пересекаются (три независимые функции в одном файле:
`todayKey`, `parseAmount`, `loadState`), что и требуется для «дай каждому
свою зону, запрети трогать чужую» из промпта занятия; (в) один из трёх
агентов (BUG-03) неожиданно занял втрое больше времени двух других —
не выравнивал искусственно, оставил как есть, это тоже честный результат:
объём кода и число связанных мест (`parseAmount`, `renderFeePreview`,
`doTransfer`, связь с BUG-01) у него оказался больше.

## Финальный вердикт

Пункт задания «Агенты: запустить и попробовать» закрыт по факту: три
независимых субагента запущены параллельно в одной главной сессии, каждый
получил свою зону и запрет трогать чужую и код продукта, результат каждого
вернулся в главную сессию и сведён в один документ — это буквально
формулировка задания («Разбейте работу на части и отдайте их субагентам —
параллельно, в одной сессии… Когда все закончат — собери результаты в один
документ»).

Что осталось открытым:
- Изоляция агентов от правки `app/` обеспечена инструкцией, а не
  ограничением набора инструментов — слабее, чем могла бы быть; факт
  соблюдения проверен постфактум через `git status`, а не гарантирован
  заранее.
- Полноценного контролируемого замера «последовательно против параллельно»
  по-прежнему нет (`REPORT.md` § 8) — приведённое здесь сравнение времени
  показывает факт параллельности этого прогона, но не сравнивает его с тем
  же заданием, выполненным одним агентом последовательно.
- Сами баги (BUG-02/03/04) остаются непочиненными — эта сессия сознательно
  ограничена диагностикой, фикс — отдельная работа со своей постановкой.

## Приложение. Диагностика и предложенные фиксы

### BUG-02 — дневной лимит по UTC (агент 1, 92176 мс, 10 обращений к инструментам)

**Диагноз.** Причина — `todayKey()` (`app/index.html:329-331`) использует
`new Date().toISOString().slice(0, 10)`, а `toISOString()` по спецификации
всегда возвращает представление в UTC. При машине в UTC+3 обнуление
дневного лимита фактически происходит в 03:00 по местному времени, а не
в полночь; ночные переводы (00:00–03:00 местного) попадают во «вчерашний»
бюджет лимита. `spentToday()` и запись `operations[].day` используют тот
же ключ — дефект системный для всей логики дневного лимита, других мест,
неявно завязанных на UTC, в файле не найдено (вывод времени в истории уже
берёт локальное время корректно).

**Fix.**
```js
// было (app/index.html:329-331)
function todayKey() {
  return new Date().toISOString().slice(0, 10);
}

// стало
function todayKey() {
  var d = new Date();
  var y = d.getFullYear();
  var m = ("0" + (d.getMonth() + 1)).slice(-2);
  var day = ("0" + d.getDate()).slice(-2);
  return y + "-" + m + "-" + day;
}
```
Формат ключа (`YYYY-MM-DD`) не меняется — совместимо с уже сохранёнными
записями. `getFullYear/getMonth/getDate` уже учитывают локальный часовой
пояс и текущий режим DST на момент вызова — дополнительной обработки
перехода на летнее/зимнее время не требуется.

**Риски.** Низкие и локальные. Данные, накопленные в `localStorage` до
фикса, посчитаны по старой (UTC) логике — возможен разовый сдвиг
классификации «сегодня/вчера» для уже сохранённых записей, окно до суток,
один раз. `tests/payments.spec.js` не трогает `todayKey`/лимит — не
ломается. Тестовое окружение (CI/headless в UTC) до и после фикса ведёт
себя одинаково, т.к. локальное время = UTC.

**Что решить человеку.** Формально в `test-plan.md`/`test-areas/transfers.md`
открытый вопрос предлагал три варианта (МСК / UTC / часовой пояс клиента) —
агент реализовал третий (локальное время устройства пользователя), это
нужно явно подтвердить как продуктовое решение (клиентские часы
недоверенные и легко подделываются — для учебного демо-стенда без сервера
это допустимо, для «настоящего» продукта обычно берут серверный/регламентный
пояс). После подтверждения — закрыть открытые вопросы в `test-plan.md`,
`test-areas/transfers.md`, `test-areas/app.md` и зафиксировать в
`app/build-brief.md` по аналогии с BUG-01.

### BUG-03 — усечение суммы при вводе (агент 2, 211262 мс, 11 обращений к инструментам)

**Диагноз.** `parseAmount()` (`app/index.html:351-353`) делает
`parseFloat(String(value).replace(",", "."))`. `parseFloat` по спецификации
разбирает читаемый **префикс** строки и молча отбрасывает нераспознанный
хвост вместо того, чтобы вернуть `NaN` для всей строки; последующая
проверка (`isFinite(amount) && amount > 0`) видит только итоговое число и
не может отличить «100» от «100, из которых отброшено „abc“». Отсюда все
усечения из таблицы бага (`"1 000"→1`, `"1,000"→1`, `"1.234,56"→1.234`,
`"100abc"→100`, `"1.2.3"→1.2`).

**Fix.** Строгая regex-валидация всей строки вместо угадывания разделителя
разрядов — обоснование: в платёжном виджете молчаливое усечение опаснее
явного отказа (списание уже необратимо, отказ — нет), а поддержка пробела
как разделителя разрядов не снимает двусмысленность формата (`1.234,56`
можно прочитать двумя способами).
```js
// было (app/index.html:351-353)
function parseAmount(value) {
  return parseFloat(String(value).replace(",", "."));
}

// стало
var AMOUNT_RE = /^-?\d+([.,]\d{1,2})?$/;
function parseAmount(value) {
  var s = String(value).trim();
  if (!AMOUNT_RE.test(s)) return NaN;
  return parseFloat(s.replace(",", "."));
}
```
В `doTransfer()` (`app/index.html:440-446`) — отдельная проверка формата
до проверки «больше нуля», с отдельным сообщением: «Сумма указана в
неверном формате. Введите число без пробелов и разделителей разрядов,
например 1000.50 или 1000,50.» Знак минуса (`-?`) в регулярке обязателен,
иначе сообщение для `APP-005` (ввод `-5`) изменится и тест-план сочтёт
это регрессией.

**Взаимодействие с BUG-01.** Грамматика (не более 2 знаков после
разделителя) закрывает дыру, отмеченную в BUG-01 «Задело»: `amount`,
прошедший валидацию, физически не может иметь больше 2 знаков после
запятой — доли копейки со стороны поля «Сумма» больше не просачиваются в
`round2(balance)`.

**Риски.** `APP-001…004, 006-008, 010-014` — не ломаются (чистые
целые/двузначно-дробные суммы без пробелов). `APP-009`/красный тест в
`tests/payments.spec.js` переходит в зелёный — это цель фикса, но
комментарий-шапку теста («APP-009 → BUG-03») нужно будет обновить отдельно.
Побочно закрывается и открытый вопрос №3 `test-plan.md` про экспоненциальную
запись (`"1e3"`) — новая грамматика её тоже отклоняет.

**Что решить человеку.** Подтвердить направление (строгий отказ, не
поддержка пробела); подтвердить, что десятичным разделителем считаются и
точка, и запятая; финальный текст сообщения об ошибке; нужен ли верхний
предел цифр в целой части (не входит в фикс по умолчанию).

### BUG-04 — крах истории при повреждённой схеме (агент 3, 89800 мс, 3 обращения к инструментам)

**Диагноз.** `loadState()` (`app/index.html:299-312`) проверяет только
`typeof parsed.balance === "number"` и `Array.isArray(parsed.operations)` —
форма элементов массива не проверяется, пустой объект `{}` проходит.
`renderHistory()` (`op.amount.toFixed(2)`, строка 416) падает на
`undefined.toFixed`. `setInterval(renderHistory, 1000)` — штатный поллинг
для окна отмены, не причина бага, но усилитель видимости: ошибка
повторяется каждую секунду, потому что `state` между тиками не меняется.
Прямое нарушение `SPEC.md` («сброс к начальному состоянию, ошибка в
консоль не выбрасывается»).

**Fix.**
```js
// новая функция валидации формы одной операции
function isValidOperation(op) {
  return op !== null && typeof op === "object" &&
    typeof op.id === "string" &&
    typeof op.recipient === "string" &&
    typeof op.amount === "number" && isFinite(op.amount) &&
    typeof op.fee === "number" && isFinite(op.fee) &&
    (op.status === "done" || op.status === "cancelled") &&
    typeof op.createdAt === "number" && isFinite(op.createdAt) &&
    typeof op.day === "string";
}

// loadState(): было — только parsed.balance/Array.isArray(parsed.operations);
// стало — плюс isFinite(parsed.balance) и цикл по operations:
for (var i = 0; i < parsed.operations.length; i++) {
  if (!isValidOperation(parsed.operations[i])) {
    return defaultState();   // одна повреждённая запись — откат ВСЕГО состояния
  }
}

// renderHistory(): defensive-барьер вторым слоем
if (!isValidOperation(op)) continue;
```
Заодно найден смежный дефект того же класса: `typeof NaN === "number"`
проходит исходную проверку баланса — добавлена `isFinite(parsed.balance)`.

**Архитектурный выбор.** Полная отбраковка состояния целиком, а не
построчная фильтрация валидных операций — обоснование: `balance` в этом
продукте не пересчитывается из `operations` (независимое поле), поэтому
частичная фильтрация не защищает баланс от рассинхронизации, зато создаёт
ложное чувство целостности денежного аудиторского следа; `spentToday()`
суммирует `status === "done"` — молчаливый пропуск повреждённых «done»-
записей ослабил бы дневной лимит как бизнес-инвариант. `SPEC.md` уже
описывает контракт как двоичный сброс, не частичное восстановление.

**Риски.** Ложных срабатываний на существующих данных не ожидается — в
кодовой базе ровно одна точка записи операций (`doTransfer`), всегда с
полным набором из семи полей; риск для будущей эволюции схемы — если
появится новое поле или статус, `isValidOperation` нужно обновлять
синхронно с записью, иначе новый легитимный формат будет считаться
повреждённым.

**Что решить человеку.** Включать ли поле `id` в обязательную схему
(баг-репорт его не упоминал, агент включил по факту использования в
`cancelOperation`); заводить ли находку по `NaN` в балансе отдельным
баг-репортом или включить в фикс BUG-04.
